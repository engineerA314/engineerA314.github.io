1. Full-duplex Speech-to-Speech Inference Engines

Nari Labs · Aug–Sep 2026

I rebuilt the runtime and scheduler to serve 80 PersonaPlex 7B conversations or 64 Nemotron VoiceChat 11B conversations on a single H100.

TL;DR

Problem
Existing serving engines used the GPU inefficiently for models that listen and speak simultaneously. vLLM-Omni supported one Nemotron conversation per H100; NVIDIA’s engines supported four to six.
Approach
I designed model-specific runtimes that batch live conversations on a common 80 ms clock, then use the time before the next audio deadline to generate tool calls and process their results.
Result
80 PersonaPlex sessions or 64 Nemotron sessions on one H100. Nemotron reached 16× NVIDIA NIM’s concurrent capacity, with a GPU cost of $0.067 per conversation-hour at full utilization.
PersonaPlex technical postNemotron technical post

Background

These models consume an audio frame and produce the next one every 80 ms. Missing that deadline can empty the playback buffer and interrupt the conversation. High average throughput is insufficient: each live session must keep up with the audio clock.

The vLLM-Omni paths I tested did not organize this workload around a shared audio clock. Sessions triggered small batches and repeated CPU–GPU synchronization. Tool processing also followed the audio cadence, so generating even a short tool-call string could take seconds. The GPU was underused, while each additional conversation increased overhead.

What I built

  1. A runtime built around the model’s audio clock. I aligned live sessions into fixed batches and optimized the end-to-end GPU execution path. CUDA Graph capture, preallocated buffers, and model-specific execution reduced repeated launch and synchronization costs.
  2. More conversations within the same memory budget. I kept model weights in BF16 and stored the temporal KV cache in FP8, halving the memory used by that cache.
  3. Fast tool use without delaying live audio. The scheduler reserves time for audio first, batches tool-call decoding in the remaining window, and processes returned text with chunked prefill sized to fit before the next deadline.
  4. Session and transport handling outside the GPU loop. I separated Opus audio processing and WebSocket I/O from model execution so networking and session turnover would not stall the GPU.

Results

PersonaPlex supported 80 simultaneous sessions with no missed 80 ms deadlines or dropped frames in a 10-minute, 3,000-token-context load test. A 30-minute session-turnover test checked session lifecycle handling. Nemotron supported 64 sessions, including 16 using tools, without missed audio deadlines or dropped frames.

Hardware: one H100 SXM 80GB. Nemotron comparisons used uninterrupted playback with a 160 ms buffer. The $0.067 figure assumes full utilization and an H100 price of $4.29/hour; engine precision differs as documented in the linked comparison.

2. Qwen3-TTS Inference Engine & Streaming API

Nari Labs · Aug–Sep 2026

I built a scheduler around Qwen3-TTS’s internal modules and served it through a streaming API, achieving #1 latency on Speko and #2 on Coval.

TL;DR

Problem
Qwen3-TTS has three generation modules with different execution costs. Running a long sequence of module jobs for one request delayed other requests’ first audio or their next playback chunk.
Approach
I made Talker, Code Predictor, and Codec jobs independently schedulable, and designed a policy that balances first-audio latency, playback deadlines, and efficient batching.
Result
Median time to first audio of 51 ms on Speko (#1) and 63 ms on Coval (#2), measured by third-party benchmarks in Aug–Sep 2026.
Open-source implementationInference technical postInput-streaming API

Background

Qwen3-TTS generates speech in three stages: Talker produces speech codes, Code Predictor completes them, and Codec turns them into audio. The modules differ in compute cost, repetition, and batching efficiency. Running a long sequence of jobs for one request can block another request’s first audio or next playback chunk.

New requests need their first audio quickly; ongoing requests need each subsequent chunk before playback runs out. I therefore needed a scheduler that could see all three modules’ pending jobs and dependencies, prioritize urgent work, and still batch similar operations efficiently.

What I built

  1. One scheduler for all module jobs. I separated Talker, Code Predictor, and Codec execution into jobs, allowing the scheduler to choose the next module and request using dependency and urgency information.
  2. A policy for first audio and continuous playback. I prioritized requests waiting for their first audio and chunks approaching their playback deadlines, while batching jobs for the same module.
  3. Lower execution cost within each module. I captured Code Predictor’s repeated work with CUDA Graphs, preallocated its KV cache, and cached Codec state so it could decode only newly generated audio.
  4. A streaming API used as a service. I developed and operated a WebSocket path that accepts text incrementally from an LLM and starts generating audio as text arrives.

3. 2B Causal Avatar Model & Training Optimization

Nari Labs · Apr–Jul 2026

I developed a 2B model that generates talking and listening avatar video from text, an image, and incoming audio, and reduced teacher training step time by 37%.

TL;DR

Problem
We needed a small, cost-efficient avatar model for real-time conversation on a single H100. It had to react to incoming audio rather than generate a complete video offline.
Approach
I extended Wan 1.3B with text, image, and audio conditioning, then implemented teacher training, causal student distillation, and training on the student’s own generated history.
Result
A 2B causal avatar model and a multi-stage training implementation. Teacher step time fell from 18.34 s to 11.55 s, and model FLOPs utilization increased from 23.3% to 37.0%.

Background

In a live conversation, future speech is unavailable. The model must generate the next video chunk using previous video and the current inputs. Small model size mattered for both generation speed and the cost of serving each conversation; the target was real-time operation on a single H100.

A causal model also feeds its own generated video back into the next step. Training only on clean reference video leaves a mismatch at inference time, allowing errors to accumulate during longer generation. The training process needed to address both generation quality and this feedback loop.

What I built

  1. A model that can generate video as the conversation unfolds. I added text, image, and audio conditioning to Wan 1.3B and implemented chunk-wise causal attention so the student could produce video incrementally.
  2. Training stages with distinct purposes. I first trained the diffusion teacher for generation quality, then used ODE distillation to transfer its behavior to the student. Self-Forcing DMD trained the student on its own generated history, and adversarial refinement further improved quality.
  3. Faster distributed training. I optimized the FSDP2 training setup and reduced overhead in RMSNorm, modulation, and RoPE. FlashAttention 4 and selective activation checkpointing improved compute and memory efficiency.

Results

4. Async-GRPO Weight Synchronization

Independent project · Oct–Nov 2025

I replaced CPU-mediated weight transfers in Red Hat’s open-source GRPO framework with direct GPU communication, reducing 7B synchronization from 224.06 s to 0.256 s.

TL;DR

Problem
Training and response generation ran on separate GPUs, but sending updated 7B weights to the workers took almost four minutes. This repeated transfer became a bottleneck.
Approach
I replaced GPU→CPU→Ray Object Store→GPU transfers with NCCL GPU-to-GPU broadcast, and reorganized worker and communication-group management.
Result
7B weight synchronization took 0.256 s instead of 224.06 s: approximately 874× faster. I also verified improvements for 0.5B and 3B models.
Code & reproduction instructionsBenchmark results

Background

GRPO is a reinforcement learning method that updates a model using rewards for several generated responses. Separating generation and training onto different GPUs allows the two workloads to overlap, but generation and log-probability workers must repeatedly receive the trainer’s latest weights.

The original transfer path copied GPU weights to CPU memory, serialized them through Ray’s Object Store, and copied them back to the destination GPU. Larger models spent increasingly long waiting for that path. I focused on eliminating those intermediate copies.

What I built

  1. Coordinated worker and communication setup. I centralized worker registration and connected the FSDP trainer and vLLM generation workers through managed role-specific pools and communication groups.
  2. Direct GPU weight broadcast. I used Ray’s collective communication support to create NCCL groups and broadcast weights from trainer rank 0 directly to generation and log-probability workers, removing CPU serialization and Object Store transfers.
  3. Reproducible before-and-after measurements. I compared both transfer paths at the same synchronization point for Qwen2.5 0.5B, 3B, and 7B, and published the benchmark configuration and reproduction steps.
